# План доведения Web Performance Auditor до production-ready

Основание: `RELEASE_REPORT.md`, текущее состояние `main` (`d20bfc3` + незакоммиченные изменения), результаты `npm run verify` и E2E 37/37.

## 1. Что считаем production-ready

Релиз считается production-ready, когда одновременно выполнены условия:

- закрыты все P0/P1-задачи из этого плана;
- must-требования ТЗ либо реализованы, либо имеют явно принятое и задокументированное ограничение с обоснованием;
- `npm run verify` и E2E проходят на чистом CI;
- проверены установка из release-артефакта, Side Panel и popup-fallback;
- проведены performance- и accessibility-проверки;
- нет известных P0/P1-дефектов;
- release воспроизводим: тег, артефакт, checksum, release notes;
- документация описывает установку, ограничения, приватность и восстановление после сбоев.

## 2. Текущее состояние

### Готово

- Критические P1-исправления и must-сценарии.
- Валидация page → content, лимиты хранения, навигационные сегменты, SPA-события.
- Консолидация метрик в экспорте, права экспериментов, DNR-cleanup.
- Исправления по code review.
- Fallback для `buffered`-наблюдателей и событие `collector-limitation`.
- Проверка `schemaVersion` при чтении и очистка несовместимых записей.
- Контраст текста и оверлеев, focus-visible, reduced motion.
- Время старта сессии в popup.
- MIT-лицензия, README, CI на Node 22 и актуальных actions.
- 95 unit-тестов, E2E 37/37, code review APPROVE.

### Не готово

- Текущие изменения не закоммичены и не отправлены в `main`.
- Обновлённый CI ещё не проверен на GitHub.
- Нет тега `v0.1.0`, GitHub Release и zip-артефакта.
- Есть must/quality-гaps: пакетная запись событий, накладные расходы коллектора, FR-14 «перемещён», статус полноты сессии, автоматизированная accessibility-проверка.

## 5. P1. Must-гaps и production-риски — 4–6 дней

### P1.1. Пакетная запись диагностических событий (NFR 4.1)

Сейчас каждое событие пишется отдельной транзакцией IndexedDB.

- [ ] Добавить `storage.saveEvents(events)` с одной транзакцией на пакет.
- [ ] Добавить буфер в `SessionManager`: размер пакета 10–20 событий или окно 50–100 мс.
- [ ] Принудительный flush при:
  - остановке сессии;
  - смене навигационного сегмента;
  - очистке/сбросе сессии;
  - достижении лимита событий;
  - ошибке записи.
- [ ] Не терять порядок событий и не превышать `maxEventsPerSession`.
- [ ] Обеспечить идемпотентность при повторной доставке.
- [ ] Добавить unit-тесты: пакет, лимит, flush, ошибка одной записи, навигация, повторный id.

**Acceptance:** при серии из 100 событий число транзакций существенно меньше 100; при stop/navigation нет потери; E2E зелёный.

### P1.2. Накладные расходы коллектора и инициализация (NFR 4.1)

Коллектор сейчас регистрируется на всех `http/https` страницах с `document_start`.

- [ ] Добавить performance-бенчмарк: fixture-страница с расширением и без.
- [ ] Измерить:
  - задержку загрузки/TBT;
  - количество long tasks;
  - memory;
  - время старта page script.
- [ ] Зафиксировать бюджет: менее 5% overhead для типового сценария.
- [ ] Если бюджет нарушен — разделить page script на:
  - лёгкий ранний сбор LCP/FCP/TTFB через buffered API;
  - тяжёлые observers/INP/longtask — при старте аудита.
- [ ] Если разделение невозможно без потери корректности — оформить decision record с обоснованием и цифрами.
- [ ] Добавить результат в `docs/performance/` или README.

**Acceptance:** есть воспроизводимый замер, а не предположение; overhead в бюджете или ограничение официально принято.

### P1.3. FR-14: удаление, замена и перемещение цели

Сейчас удаление/замена определяются через `isConnected`, явное перемещение не отслеживается.

- [ ] При подсветке сохранять структурный якорь: parent, previous/next sibling, tag, selector.
- [ ] В scoped MutationObserver проверять:
  - target отсоединён;
  - selector теперь указывает на другой узел;
  - изменился parent или позиционные соседи.
- [ ] При изменении показывать «Элемент изменился или больше недоступен».
- [ ] Не подсвечивать автоматически новый узел по тому же selector, если это уже не исходная цель.
- [ ] Добавить E2E:
  - удаление;
  - замена узла с тем же selector;
  - перемещение внутри DOM.
- [ ] Unit-тест на функцию сравнения структурного якоря, если она вынесена в утилиту.

**Acceptance:** все три сценария дают статус unavailable, старый overlay скрыт, новый узел не подсвечивается без действия пользователя.

### P1.4. Статус полноты сессии

- [ ] Вычислять полноту сессии по:
  - недоступным/неизмеренным метрикам;
  - событиям `collector-limitation`;
  - отсутствию INP без взаимодействия;
  - unsupported API.
- [ ] Показывать компактный статус в side panel: «Полная» / «Частичная» / «Ограниченная».
- [ ] Раскрывать причины и время начала наблюдения.
- [ ] Включить тот же статус в JSON/Markdown-отчёт.
- [ ] Добавить unit-тесты классификации.

**Acceptance:** пользователь видит, почему данные неполные, не открывая сырые события.

### P1.5. Storage lifecycle и схема

- [ ] Оформить политику `SCHEMA_VERSION`: какие версии читаются, какие мигрируют, какие удаляются.
- [ ] Решить, нужна ли миграция v1 → v2 для первого публичного релиза.
- [ ] Если миграция не нужна — явно задокументировать разрушительное поведение.
- [ ] Добавить тест очистки несовместимой active-сессии и running-эксперимента.
- [ ] Проверить, что restore не оставляет указатель на удалённую сессию.

**Acceptance:** поведение предсказуемо, старые записи не ломают UI, retention не застревает.

### P1.6. Accessibility-гейт

- [ ] Добавить `axe-core` как dev dependency.
- [ ] Прогнать автоматический аудит для:
  - side panel: overview, events, experiments, data;
  - popup;
  - пустого/ошибочного состояния.
- [ ] Исправить serious/critical нарушения.
- [ ] Вручную проверить:
  - полный keyboard-only сценарий;
  - focus-visible;
  - контраст;
  - screen-reader labels у метрик и кнопок.
- [ ] Добавить `npm run test:a11y` и включить в CI, если стабильно.

**Acceptance:** нет serious/critical axe-нарушений; keyboard-only сценарий проходим.

## 9. Release gates

Релиз `v0.1.0` блокируется, если:

- есть незакоммиченные изменения;
- CI красный;
- `npm run verify` или E2E падают;
- есть известный P0/P1-дефект;
- не проверена установка из артефакта;
- performance-бюджет превышен без принятого decision record;
- axe содержит serious/critical;
- release notes скрывают известные ограничения.
