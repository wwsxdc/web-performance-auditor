# План доведения Web Performance Auditor до production-ready

Основание: `RELEASE_REPORT.md`, `main` после P0–P2, `npm run verify` (124 теста), E2E 41/41, a11y 15/15.

## 1. Что считаем production-ready

Релиз считается production-ready, когда одновременно выполнены условия:

- закрыты все P0/P1-задачи из этого плана;
- must-требования ТЗ либо реализованы, либо имеют явно принятое и задокументированное ограничение с обоснованием;
- `npm run verify` и E2E проходят на чистом CI;
- проверены установка из release-артефакта, Side Panel и popup-fallback;
- проведены performance- и accessibility-проверки;
- нет известных P0/P1-дефектов;
- release воспроизводим: тег, артефакт, checksum, release notes;
- документация описывает установку, ограничения, приватность и восстановление после сбоев.

## 5. P1. Must-гaps и production-риски — 4–6 дней

### P1.1. Пакетная запись диагностических событий (NFR 4.1)

Сейчас каждое событие пишется отдельной транзакцией IndexedDB.

- [x] Добавить `storage.saveEvents(events)` с одной транзакцией на пакет.
- [x] Добавить буфер в `SessionManager`: размер пакета 10–20 событий или окно 50–100 мс.
- [x] Принудительный flush при:
  - остановке сессии;
  - смене навигационного сегмента;
  - очистке/сбросе сессии;
  - достижении лимита событий;
  - ошибке записи.
- [x] Не терять порядок событий и не превышать `maxEventsPerSession`.
- [x] Обеспечить идемпотентность при повторной доставке.
- [x] Добавить unit-тесты: пакет, лимит, flush, ошибка одной записи, навигация, повторный id.

**Acceptance:** при серии из 100 событий число транзакций существенно меньше 100; при stop/navigation нет потери; E2E зелёный.

### P1.2. Накладные расходы коллектора и инициализация (NFR 4.1)

Коллектор сейчас регистрируется на всех `http/https` страницах с `document_start`.

- [x] Добавить performance-бенчмарк: fixture-страница с расширением и без.
- [x] Измерить:
  - задержку загрузки/TBT;
  - количество long tasks;
  - memory;
  - время старта page script.
- [x] Зафиксировать бюджет: менее 5% overhead для типового сценария.
- [x] Если бюджет нарушен — разделить page script на:
  - лёгкий ранний сбор LCP/FCP/TTFB через buffered API;
  - тяжёлые observers/INP/longtask — при старте аудита.
- [x] Если разделение невозможно без потери корректности — оформить decision record с обоснованием и цифрами.
- [x] Добавить результат в `docs/performance/` или README.

**Acceptance:** есть воспроизводимый замер, а не предположение; overhead в бюджете или ограничение официально принято.

### P1.3. FR-14: удаление, замена и перемещение цели

Сейчас удаление/замена определяются через `isConnected`, явное перемещение не отслеживается.

- [x] При подсветке сохранять структурный якорь: parent, previous/next sibling, tag, selector.
- [x] В scoped MutationObserver проверять:
  - target отсоединён;
  - selector теперь указывает на другой узел;
  - изменился parent или позиционные соседи.
- [x] При изменении показывать «Элемент изменился или больше недоступен».
- [x] Не подсвечивать автоматически новый узел по тому же selector, если это уже не исходная цель.
- [x] Добавить E2E:
  - удаление;
  - замена узла с тем же selector;
  - перемещение внутри DOM.
- [x] Unit-тест на функцию сравнения структурного якоря, если она вынесена в утилиту.

**Acceptance:** все три сценария дают статус unavailable, старый overlay скрыт, новый узел не подсвечивается без действия пользователя.

## 9. Release gates

Релиз `v0.1.0` блокируется, если:

- есть незакоммиченные изменения;
- CI красный;
- `npm run verify` или E2E падают;
- есть известный P0/P1-дефект;
- не проверена установка из артефакта;
- performance-бюджет превышен без принятого decision record;
- axe содержит serious/critical;
- release notes скрывают известные ограничения.
